# デザインレビュースキル

実装後のページ/コンポーネントに対して、視覚的一貫性・アクセシビリティ・レスポンシブ対応を中心とした UI/UX 監査を実施する。

> プロジェクト設定・技術スタック・制約は [CLAUDE.md](/Users/uchan/d3m_condo_bylaws_pj/CLAUDE.md) を参照。
> アクセシビリティ基準は [accessibility-guide スキル](/Users/uchan/d3m_condo_bylaws_pj/.claude/skills/accessibility-guide/SKILL.md) を参照。

## ターゲットユーザー

**50〜70代のマンション理事会メンバー**。高齢者でも迷わず使える UI が必須。
デジタルリテラシーが高くないユーザーを前提に、読みやすさ・操作しやすさを最優先で評価する。

## Preamble（実行前チェック）

1. CLAUDE.md を読み、技術スタック・UI 制約を確認する
2. accessibility-guide スキルの基準（フォント・コントラスト・タッチターゲット・印刷）を確認する
3. レビュー対象を特定する（引数 or 最近の変更ファイル）

> **注意**: Preamble のチェックでブロッカーが見つかった場合は、ワークフローを開始せず即座に **BLOCKED** または **NEEDS_CONTEXT** で報告する。

## ワークフロー

### Step 1: 対象の特定

#### 引数が指定された場合
- ページパス（例: `/review`, `/chat`）→ 対応する `src/app/` 配下のページコンポーネントを特定
- コンポーネント名（例: `ArticleDiffView`）→ `src/components/` または `src/domains/` 配下を検索

#### 引数なしの場合
```bash
cd /Users/uchan/d3m_condo_bylaws_pj
git diff --name-only HEAD~5 HEAD -- '*.tsx' '*.css'
```
最近変更された UI ファイル（`.tsx`, `.css`）を対象にする。変更がなければ **NEEDS_CONTEXT** で報告。

### Step 2: コード読み取り

対象コンポーネントのソースコードを読み、以下を把握する:
- コンポーネントの階層構造（親子関係）
- 使用している shadcn/ui コンポーネント
- Tailwind CSS クラスの使用パターン
- 状態管理（Zustand ストア、ローカルステート）
- 条件分岐による表示切り替え（ローディング、エラー、空状態等）

### Step 3: 6軸レビュー

#### a. 視覚的一貫性

| チェック項目 | 基準 |
|-------------|------|
| 色の統一 | プロジェクトのカラーパレット（`globals.css` の CSS 変数）に準拠 |
| 余白の統一 | Tailwind のスペーシングスケール（`p-4`, `gap-6` 等）を一貫して使用 |
| フォントサイズ | `text-base`（16px）以上で統一、見出し階層が明確 |
| ボーダー・角丸 | shadcn/ui のデフォルトスタイルと一貫 |
| アイコン | Lucide React を使用、サイズ統一（`w-4 h-4` or `w-5 h-5`） |
| コンポーネント再利用 | 既存の shadcn/ui コンポーネントで代替できる独自実装がないか |

#### b. アクセシビリティ（WCAG 2.1 AA + 高齢者対応）

| チェック項目 | 基準 |
|-------------|------|
| フォントサイズ | 本文 16px 以上、重要テキスト 18px 以上、見出し 24px 以上 |
| 行間 | `leading-relaxed`（1.75）以上 |
| コントラスト比 | テキスト vs 背景: 4.5:1 以上、大テキスト: 3:1 以上 |
| タッチターゲット | インタラクティブ要素 44x44px 以上 |
| 色だけに頼らない | 色情報にテキスト・記号・アイコンを併用 |
| ARIA 属性 | 適切な `aria-label`, `role`, `aria-live` の使用 |
| キーボード操作 | Tab 順序、フォーカス表示（`focus-visible`） |
| フォーム | `<label>` の紐付け、エラーメッセージの明示 |

#### c. レスポンシブ対応

| チェック項目 | 基準 |
|-------------|------|
| ブレークポイント | `sm:`, `md:`, `lg:` の適切な使用 |
| テーブル | 横スクロール対応（`overflow-x-auto`）またはカード表示への切り替え |
| ナビゲーション | モバイルでのハンバーガーメニュー/ドロワー |
| 画像・SVG | `max-w-full` でオーバーフロー防止 |
| タッチ操作 | モバイルでのスワイプ、長押し等の考慮 |
| 文字サイズ | モバイルでも 14px 未満にならないこと |

#### d. インタラクション状態

| チェック項目 | 基準 |
|-------------|------|
| ローディング状態 | スケルトン UI またはスピナーの表示 |
| 空状態 | データがない場合の案内メッセージ |
| エラー状態 | ユーザーに分かりやすいエラーメッセージ + リトライ導線 |
| 成功状態 | 操作完了のフィードバック（トースト通知等） |
| disabled 状態 | ボタン等の非活性時の視覚的区別 |
| ホバー/フォーカス | hover, focus-visible スタイルの存在 |
| プログレス表示 | 長時間処理の進捗表示（SSE ストリーミング等） |

#### e. 印刷対応

| チェック項目 | 基準 |
|-------------|------|
| `@media print` | 印刷用スタイルの有無 |
| ナビ/サイドバー非表示 | `print:hidden` で操作系 UI を非表示 |
| 背景色 | 印刷時に白背景に切り替え |
| 差分ハイライト | 追加=下線、削除=取消線、修正=太字（色に頼らない） |
| ページ区切り | `break-before`, `break-after`, `break-inside` の適切な使用 |
| URL 展開 | リンクの URL を表示（`a::after { content: " (" attr(href) ")" }`） |

> エクスポート機能に関連するページは特に印刷対応を重点チェックする。

#### f. 日本語タイポグラフィ

| チェック項目 | 基準 |
|-------------|------|
| 改行位置 | `word-break: break-all` ではなく `overflow-wrap: break-word` を使用 |
| 長文テキスト | 条文等の長いテキストに `max-w-prose`（65ch）相当の幅制限 |
| 括弧・句読点 | 全角括弧、全角句読点の表示確認 |
| 数字混在 | 条番号（第○条）等の和文/数字混在テキストの可読性 |
| 禁則処理 | 句読点・閉じ括弧が行頭に来ないこと |
| フォント | Noto Sans JP の適用確認 |

### Step 4: スクリーンショットとの比較

`kiyaku-assist-v2/e2e/screenshots/` に既存のスクリーンショットがあれば:
1. 対象ページ/コンポーネントに該当するスクリーンショットを特定
2. コードから推測されるレイアウトとスクリーンショットを比較
3. 視覚的な乖離があれば指摘に含める

スクリーンショットが存在しない場合はスキップし、「スクリーンショットなし」と記載する。

### Step 5: 修正提案

発見した問題を以下のフォーマットで報告する:

```markdown
## デザインレビュー結果: [対象ページ/コンポーネント名]

### CRITICAL（即座に修正が必要）
- **[軸名] 問題の要約**
  - 該当箇所: `ファイルパス:行番号`
  - 現状: 具体的な問題の説明
  - 修正案:
    ```tsx
    // 修正コード
    ```

### HIGH（次回リリースまでに修正）
- ...

### MEDIUM（改善推奨）
- ...

### LOW（将来的に対応）
- ...

### 問題なし
- [軸名]: チェック結果の概要
```

**優先度の基準**:
| 優先度 | 基準 |
|--------|------|
| CRITICAL | アクセシビリティ違反（コントラスト不足、タッチターゲット不足）、レイアウト崩れ |
| HIGH | インタラクション状態の欠落、レスポンシブ未対応 |
| MEDIUM | 視覚的一貫性の軽微な乱れ、日本語タイポグラフィの改善 |
| LOW | 印刷対応の細かい調整、コード品質の改善 |

### Step 6: アトミックコミットで修正

ユーザーが修正を承認した場合:
1. 問題ごとに1件ずつ修正する
2. 修正後、対応するテストがあれば実行して確認する
3. 1件の修正ごとに1コミットを作成する

```bash
# コミットメッセージの例
git commit -m "fix(a11y): ArticleDiffView のコントラスト比を 4.5:1 以上に修正"
git commit -m "fix(responsive): ReviewTable にモバイル横スクロール対応を追加"
git commit -m "fix(typography): 条文表示の改行位置を overflow-wrap: break-word に変更"
```

> **注意**: 修正は1件ずつコミットする。複数の修正を1つのコミットにまとめない。

## 技術スタック参照

- **UI ライブラリ**: shadcn/ui + Radix UI

## エスカレーションプロトコル

以下の条件で作業を停止し、ユーザーに報告する:

- **3回の試行失敗**: 同じアプローチを3回試して解決しない場合
- **セキュリティの不確実性**: 認証、データ漏洩、非弁リスクに関する判断に迷う場合
- **ドメイン境界の逸脱**: 修正が複数ドメインにまたがり、影響範囲が不明確な場合

報告フォーマット:
- **REASON**: なぜ停止したか
- **ATTEMPTED**: 試行した内容（最大3つ）
- **RECOMMENDATION**: 推奨する次のステップ

## 完了報告

実行結果を以下のいずれかで報告する:
- **DONE**: 6軸レビュー完了、問題なし（または全修正済み）
- **DONE_WITH_CONCERNS**: レビュー完了、未修正の指摘事項あり（優先度別リスト提示）
- **BLOCKED**: レビュー対象の特定に失敗（ファイルが見つからない等）
- **NEEDS_CONTEXT**: レビュー対象の指定が必要（引数なし + 最近の UI 変更なし）
