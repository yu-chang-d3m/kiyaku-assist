# 調査スキル — Iron Law: No Fixes Without Investigation First

> プロジェクト設定・技術スタック・制約は [CLAUDE.md](/Users/uchan/d3m_condo_bylaws_pj/CLAUDE.md) を参照。

## 基本原則

- **推測で修正しない** — 必ずコードとログで裏付けを取る
- **場当たり的な修正（バリデーション緩和等）は禁止** — 正しいデータフローを構築する
- **仮説は最大3つ** — 3つ全て外れたらエスカレーションする
- **検証結果は全て記録** — 成功も失敗も証拠として残す

## Preamble（実行前チェック）

1. CLAUDE.md を読み、プロジェクト設定・アーキテクチャを確認する
2. 引数から問題の概要を把握する（不足ならユーザーに質問）
3. `kiyaku-assist-v2/` ディレクトリが存在することを確認
4. `git status` で未コミットの変更を確認（調査前の状態を把握）

> **注意**: Preamble で問題の概要が不明な場合は、ワークフローを開始せず即座に **NEEDS_CONTEXT** で報告する。

## ワークフロー手順

### Step 1: 問題の定義

問題を以下の3要素で明確化する:

| 項目 | 内容 |
|------|------|
| **再現手順** | 問題を再現するための具体的な操作手順 |
| **期待値** | 本来あるべき動作 |
| **実際の挙動** | 現在起きている動作（エラーメッセージ含む） |

- ユーザーの報告が曖昧な場合は、具体的な質問で明確化する
- エラーメッセージがあれば、そのまま記録する
- スクリーンショットやログがあれば参照する

### Step 2: 影響範囲の特定

#### 2a. 関連ドメインの特定

6ドメインのどれに該当するかを特定する:

| ドメイン | 責務 | 主要ファイル |
|---------|------|-------------|
| ingestion | PDF/Word/テキストのパース | `src/domains/ingestion/` |
| analysis | ギャップ分析（RAG + Claude） | `src/domains/analysis/` |
| drafting | 改定条文ドラフト生成 | `src/domains/drafting/` |
| review | 決定状態管理（イベント駆動） | `src/domains/review/` |
| chat | RAG 問答 + 非弁ガードレール | `src/domains/chat/` |
| export | Markdown/CSV/PDF 出力 | `src/domains/export/` |

#### 2b. データフローの追跡

DDD + Clean Architecture の依存方向を意識してトレースする:

```
UI コンポーネント → API Route → ドメインロジック → shared ユーティリティ
   (app/)            (app/api/)    (domains/)          (shared/)
```

- 依存方向の逆転（domains/ → app/ への参照）がないか確認
- `shared/` 経由以外のドメイン間依存がないか確認

#### 2c. 関連ファイルのリストアップ

問題に関連するファイルを全てリストアップする:
- API Route（`src/app/api/`）
- ドメインロジック（`src/domains/{domain}/`）
- 型定義（`types.ts`）とスキーマ（`schemas.ts`）
- フロント側コンポーネント（`src/app/`）
- テストファイル（`__tests__/`）

### Step 3: 仮説の構築

最大3つの仮説を**優先度順**にリスト化する:

```
仮説 1 (最有力): [具体的な仮説]
  根拠: [なぜこの仮説が最有力か]
  検証方法: [どう検証するか]

仮説 2: [具体的な仮説]
  根拠: [なぜこの仮説を考えるか]
  検証方法: [どう検証するか]

仮説 3: [具体的な仮説]
  根拠: [なぜこの仮説を考えるか]
  検証方法: [どう検証するか]
```

#### 仮説構築のヒント

- **型の不整合**: `types.ts` と `schemas.ts` の定義が一致しているか
- **API とフロントの保存経路**: DB/API にフィールドがあってもフロントが呼んでいなければデータは消える
- **RAG パイプライン**: Vertex AI Search のクエリ → Claude の生成の間でデータが欠落していないか
- **非同期処理**: SSE ストリーミングのエラーハンドリング漏れ
- **Firebase**: セキュリティルール、Firestore のデータ構造の不整合
- **環境変数**: `apphosting.yaml` の設定漏れ

### Step 4: 検証

各仮説を順番に検証する。検証手段:

1. **コード読み** — 関連ファイルを読んでロジックを追跡
2. **ログ確認** — Pino の構造化ログ、ブラウザコンソール、Cloud Logging
3. **テスト実行** — 既存テストの実行、または最小限の再現テストの作成
4. **型チェック** — `npm run typecheck` でコンパイルエラーを確認

#### 検証結果の記録フォーマット

各仮説の検証結果を以下のフォーマットで記録する:

```
仮説 N: [仮説の内容]
検証方法: [実施した検証]
結果: CONFIRMED / REJECTED / INCONCLUSIVE
証拠: [具体的なコード箇所、ログ出力、テスト結果]
```

### Step 5: 根本原因の特定

- **仮説が CONFIRMED** → Step 6 へ進む
- **全仮説が REJECTED** → エスカレーションプロトコルを発動（後述）
- **INCONCLUSIVE あり** → 追加の検証手段を検討し、それでも判断不能ならエスカレーション

### Step 6: 修正案の提示

根本原因が特定できた場合、修正案を提示する:

| 項目 | 内容 |
|------|------|
| **根本原因** | 特定された原因の概要 |
| **修正対象ファイル** | 変更が必要なファイルの一覧 |
| **修正方針** | 正しいデータフローの構築方針 |
| **影響範囲** | 修正による他ドメインへの影響 |
| **テスト計画** | 修正を検証するためのテスト |

#### 修正案のルール

- **場当たり的な修正は禁止**: バリデーション緩和、`any` 型への変更、`try-catch` で握り潰し等は提案しない
- **正しいデータフローを構築する**: 型定義 → スキーマ → ドメインロジック → API → UI の順で整合性を取る
- **修正は提案のみ**: 実際の修正はユーザーの承認後に実行する

## エスカレーションプロトコル

### 3回仮説失敗 → BLOCKED

3つの仮説が全て棄却された場合、**即座に BLOCKED** ステータスで報告する:

```
REASON: [なぜ根本原因を特定できなかったか]
ATTEMPTED:
  - 仮説 1: [内容] → REJECTED（[理由]）
  - 仮説 2: [内容] → REJECTED（[理由]）
  - 仮説 3: [内容] → REJECTED（[理由]）
RECOMMENDATION: [次に試すべきアプローチ、必要な情報、巻き込むべき人]
```

### セキュリティ関連 → 即座にエスカレーション

以下の場合は仮説検証を中断し、即座にユーザーに報告する:

- **非弁ガードレールの不備**: chat ドメインのバグは法的リスクに直結
- **認証・認可の不備**: Firebase セキュリティルールの問題
- **データ漏洩の可能性**: 他ユーザーのデータが参照できる状態
- **API キーの露出**: クライアントサイドへの秘密情報の漏洩

## プロジェクト固有の注意点

### DDD + Clean Architecture

- 依存方向: `app/` → `domains/` → `shared/`（逆依存は禁止）
- ドメイン間の直接依存は禁止（`shared/` 経由のみ）
- 問題の原因が依存方向の逆転にある場合は、アーキテクチャレベルの修正を提案する

### RAG パイプライン（Vertex AI Search + Claude）

- 検索: `src/shared/ai/search.ts` のリトリーバー設定を確認
- キャッシュ: Firestore `aiCache` コレクション（SHA-256 キー、TTL 30日）
- キャッシュヒット/ミスの切り分けが重要

### 技術的制約の確認ポイント

- Zod: `import * as z from "zod/v4"` で統一されているか
- `"use server"` ファイル: Zod スキーマを export していないか
- pdf-parse: 動的 import になっているか
- Firebase Client SDK: モジュールレベルで初期化していないか
- Pino: 引数順が `(obj, msg)` になっているか

## 完了報告

実行結果を以下のいずれかで報告する:
- **DONE**: 根本原因を特定し、修正案を提示済み
- **DONE_WITH_CONCERNS**: 根本原因は特定したが、修正に伴うリスクあり（リスト提示）
- **BLOCKED**: 3回の仮説検証が全て失敗、またはセキュリティエスカレーション
- **NEEDS_CONTEXT**: 問題の再現手順や追加情報が必要（質問を提示）
