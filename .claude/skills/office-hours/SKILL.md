# 問題フレーミングスキル

> プロジェクト設定・技術スタック・制約は [CLAUDE.md](/Users/uchan/d3m_condo_bylaws_pj/CLAUDE.md) を参照。

## Preamble（実行前チェック）

1. CLAUDE.md を読み、プロジェクト設定・6ドメイン構成を確認する
2. 引数から問題の概要を把握する
3. 関連するドメイン・ファイルを特定するため、既存コードを軽く探索する

## Step 1: 6つの質問

以下の6つの質問を順番にユーザーに確認する。引数から推測できる回答は仮説として提示し、ユーザーの確認を求める。

### a. 需要 — この機能/修正の需要は何か？
- 誰が必要としているか（管理組合理事、管理会社担当者、システム管理者）
- なぜ必要か（法改正対応、業務効率化、ユーザー要望）
- 頻度はどの程度か（毎日使う / 年1回のみ）

### b. 現状 — 今どうなっているか？
- 既存の回避策や代替手段はあるか
- 関連する既存コードの状態（どのドメインに何があるか）
- 技術的負債やブロッカーの有無

### c. 成功の定義 — 何をもって完了とするか？
- ユーザーが確認できる完了条件
- 計測指標（処理時間、エラー率、カバレッジ等）
- 「これが動けば OK」の最小シナリオ

### d. リスク — 何が壊れる可能性があるか？
- **法的リスク**: 非弁行為に該当しないか、改正法の解釈は正確か
- **セキュリティ**: 認証・認可、データ漏洩、Firebase ルール
- **パフォーマンス**: API レイテンシ、Firestore 読み取りコスト
- **既存機能への影響**: 回帰リスク

### e. 制約 — 何に縛られているか？
- 技術的制約（CLAUDE.md の「絶対守るべき技術制約」8項目）
- 期限（法改正施行日: 2026年4月）
- コスト（Claude API / Vertex AI Search の利用量）
- ドメイン境界（6ドメイン間の直接依存は禁止）

### f. 最小実装（MVP）— 最低限何があれば十分か？
- フル実装から削れるもの
- 後回しにできるもの（Phase 分割）
- MVP で検証したい仮説

## Step 2: 設計ドキュメント出力

6つの質問への回答を元に、以下の設計ドキュメントを生成する:

```markdown
## 設計サマリー

### 1行サマリー
[問題と解決策を1行で]

### 影響ドメイン
- [ ] ingestion（PDF/Word パース）
- [ ] analysis（ギャップ分析）
- [ ] drafting（改定条文ドラフト）
- [ ] review（決定状態管理）
- [ ] chat（RAG 問答）
- [ ] export（出力）
- [ ] shared（横断関心事）

### 変更の概要（依存方向順）
1. **型定義**: [追加・変更する型]
2. **ドメインロジック**: [ビジネスルールの追加・変更]
3. **API Route**: [エンドポイントの追加・変更]
4. **UI**: [画面の追加・変更]

### テスト戦略
- Unit: [何をテストするか]
- E2E: [どのシナリオをカバーするか]
- 手動確認: [自動化が難しい確認項目]

### リスクと緩和策
| リスク | 影響度 | 緩和策 |
|--------|--------|--------|
| ... | HIGH/MEDIUM/LOW | ... |

### MVP スコープ
- Phase 1（今回）: [最小実装の範囲]
- Phase 2（後日）: [追加実装の範囲]
```

## Step 3: 次のステップ提案

設計ドキュメントの内容に基づき、最適な次のアクションを提案する:

| 状況 | 推奨アクション |
|------|---------------|
| 新機能追加（複数ドメインにまたがる） | `/add-feature` でフルフロー実行 |
| 既存機能の調査・デバッグが必要 | `/investigate` で原因調査 |
| 小規模な修正（1ファイル程度） | 直接実装してテスト |
| 設計に不安がある | ユーザーと追加議論 |

## ドメイン固有の考慮事項

### マンション管理規約の特殊性
- **非弁リスク**: AI が法的助言を行う機能は、必ず「参考情報であり法的助言ではない」旨のディスクレーマーを含める
- **法改正追従**: 改正区分所有法（2026年4月施行）と令和7年改正標準管理規約が基準
- **正確性最優先**: 条文の引用・参照は正確でなければならない（幻覚は許容されない）
- **高齢者ユーザー**: UI は WCAG 2.1 AA + 大きなタッチターゲット（44x44px 以上）

## エスカレーションプロトコル

以下の条件で作業を停止し、ユーザーに報告する:

- **3回の試行失敗**: 同じアプローチを3回試して解決しない場合
- **セキュリティの不確実性**: 認証、データ漏洩、非弁リスクに関する判断に迷う場合
- **ドメイン境界の逸脱**: 修正が複数ドメインにまたがり、影響範囲が不明確な場合

報告フォーマット:
- **REASON**: なぜ停止したか
- **ATTEMPTED**: 試行した内容（最大3つ）
- **RECOMMENDATION**: 推奨する次のステップ

## 完了報告

実行結果を以下のいずれかで報告する:
- **DONE**: 6つの質問を確認し、設計ドキュメントと次のステップを提示完了
- **DONE_WITH_CONCERNS**: 設計方針は決まったが未解決のリスクや懸念あり（詳細提示）
- **BLOCKED**: 要件が矛盾している、または技術的に実現困難（理由と代替案を提示）
- **NEEDS_CONTEXT**: 6つの質問のうち回答が不足しており、ユーザーの追加情報が必要
