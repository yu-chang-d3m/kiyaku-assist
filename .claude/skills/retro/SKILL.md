# 振り返りスキル — コミット履歴から開発インサイトを可視化

> プロジェクト設定・技術スタック・制約は [CLAUDE.md](/Users/uchan/d3m_condo_bylaws_pj/CLAUDE.md) を参照。

## 基本原則

- **データに基づく振り返り** — 感覚ではなく、コミット履歴から定量的なインサイトを導出する
- **改善機会の提示** — 数値の羅列ではなく、次のアクションにつながる分析を行う
- **DDD ドメイン単位の可視化** — 6ドメイン + shared + app でアーキテクチャの健全性を把握する

## Preamble（実行前チェック）

1. CLAUDE.md を読み、プロジェクト設定・アーキテクチャを確認する
2. 引数から分析期間を特定する（不明な場合はデフォルト: 直近1週間）
3. リポジトリルートで `git log` が実行可能なことを確認する
4. `kiyaku-assist-v2/` ディレクトリが存在することを確認

> **注意**: Git リポジトリが存在しない、またはコミットが0件の場合は **BLOCKED** で報告する。

## ワークフロー手順

### Step 1: 期間の特定

引数を解釈して `--since` / `--until` パラメータを決定する:

| 引数 | 解釈 |
|------|------|
| `week` (デフォルト) | 直近7日間 |
| `month` | 直近30日間 |
| `sprint` | 直近14日間 |
| `YYYY-MM-DD..YYYY-MM-DD` | 指定範囲 |
| `YYYY-MM-DD` | その日から今日まで |

- 引数が省略された場合は `week`（直近7日間）を使用する
- 不明な形式の場合はユーザーに確認する（**NEEDS_CONTEXT**）

### Step 2: コミット分析

`git log --stat --since=<start> --until=<end>` で以下を集計する:

#### 2a. 基本指標

- **コミット総数**
- **変更行数**: 追加行数 / 削除行数
- **変更ファイル数**: ユニークファイル数
- **アクティブ日数**: コミットがあった日数 / 期間中の総日数

#### 2b. コミットカテゴリ別内訳

コミットメッセージの prefix から分類する:

| カテゴリ | prefix パターン |
|---------|----------------|
| feat | `feat:`, `feat(` |
| fix | `fix:`, `fix(` |
| refactor | `refactor:`, `refactor(` |
| chore | `chore:`, `chore(` |
| docs | `docs:`, `docs(` |
| test | `test:`, `test(` |
| style | `style:`, `style(` |
| perf | `perf:`, `perf(` |
| ci | `ci:`, `ci(` |
| other | 上記に該当しないもの |

#### 2c. 日別コミット分布

日付ごとのコミット数を表示する（簡易ヒストグラム）。

#### 2d. ファイル別変更頻度（ホットスポット）

変更回数が多い上位10ファイルをリストアップする。
頻繁に変更されるファイルはリファクタリング候補の可能性がある。

### Step 3: ドメイン別分析

DDD 6ドメイン + 横断レイヤーごとの変更量を集計する:

| ドメイン / レイヤー | パスパターン |
|-------------------|-------------|
| ingestion | `src/domains/ingestion/` |
| analysis | `src/domains/analysis/` |
| drafting | `src/domains/drafting/` |
| review | `src/domains/review/` |
| chat | `src/domains/chat/` |
| export | `src/domains/export/` |
| shared | `src/shared/` |
| app (UI/API) | `src/app/` |
| config / root | 上記以外の `kiyaku-assist-v2/` 内ファイル |
| project root | `kiyaku-assist-v2/` 外のファイル（docs, scripts 等） |

各ドメインについて:
- コミット数（そのドメインのファイルを含むコミット数）
- 変更ファイル数
- 追加/削除行数

### Step 4: テスト健全性

#### 4a. テストファイルの変更

期間中に変更されたテストファイル（`__tests__/`, `*.test.ts`, `*.spec.ts`）を集計する。

#### 4b. テスト / 実装コードの比率

期間中の変更において:
- テストコードの変更行数
- 実装コードの変更行数
- テスト比率 = テスト変更行数 / 全変更行数

#### 4c. テストなしドメインの検出

実装コードが変更されたがテストファイルの変更がないドメインを警告する。

### Step 5: Shipping streak

- **連続コミット日数**: 連続でコミットがあった最長日数
- **最も活発な曜日**: 曜日別コミット数
- **最も活発な時間帯**: 時間帯別コミット数（午前/午後/夜間）

### Step 6: 改善機会の提示

分析結果から以下の改善機会を導出する:

| カテゴリ | 検出条件 | 提案 |
|---------|---------|------|
| テスト不足 | 実装変更ありだがテスト変更なしのドメイン | テスト追加を推奨 |
| ホットスポット | 変更回数が5回以上のファイル | リファクタリング候補 |
| ドメイン偏り | 変更が1ドメインに集中（全体の70%以上） | 他ドメインへの影響確認を推奨 |
| fix 多発 | fix カテゴリが全体の40%以上 | 品質改善策の検討を推奨 |
| docs 不足 | feat/refactor が多いが docs が0 | ドキュメント更新を推奨 |
| 大規模変更 | 1コミットで300行以上の変更 | コミット分割を推奨 |

## エスカレーションプロトコル

以下の条件で作業を停止し、ユーザーに報告する:

- **3回の試行失敗**: 同じアプローチを3回試して解決しない場合
- **セキュリティの不確実性**: 認証、データ漏洩、非弁リスクに関する判断に迷う場合
- **ドメイン境界の逸脱**: 修正が複数ドメインにまたがり、影響範囲が不明確な場合

報告フォーマット:
- **REASON**: なぜ停止したか
- **ATTEMPTED**: 試行した内容（最大3つ）
- **RECOMMENDATION**: 推奨する次のステップ

## 完了報告

実行結果を以下のいずれかで報告する:
- **DONE**: 振り返りレポートの出力完了
- **DONE_WITH_CONCERNS**: レポート出力済みだが、重大な改善機会あり（リスト提示）
- **BLOCKED**: Git リポジトリが見つからない、またはコミットが0件
- **NEEDS_CONTEXT**: 分析期間が不明確（質問を提示）
