# 規約改正アウトプット品質向上のための設計思想と要件

**作成日**: 2026-03-28
**更新日**: 2026-03-28（コード分析結果を追記 → 理事会ミーティング知見を追記）
**文脈**: Claudeが直接生成したWord文書と、キヤクアシストv2アプリのアウトプットの品質差を分析し、アプリ側に反映するための設計思想ドキュメント。2026-03-28の理事会・管理会社ミーティングで判明した実務フローを反映済み。

---

## 1. 前提：なぜ直接生成の方が「読みやすい」と感じられたか

### 1.1 根本的な違い

キヤクアシストv2は**「規約の差分を検出し、ユーザーがレビューするためのUI」**として設計されている。
一方、Claudeが直接作成したWord文書は**「理事会に印刷配布して検討するための読み物」**として設計された。

この違いは目的の違いではなく、**情報設計のレイヤーの違い**にある。

| 観点 | アプリのアプローチ | 直接生成のアプローチ |
|------|-------------------|---------------------|
| 構造の単位 | 条文（article）単位 | 課題（issue/gap）単位 |
| 提示順序 | 条文番号順 | 優先度順 |
| 文脈の提供 | 「何が変わるか」の事実 | 「なぜ変えるべきか」の理由 + 背景 |
| 読者の想定行動 | 採用/修正/保留を判断 | まず全体像を把握し、方針を議論 |
| 視覚的な設計 | UIコンポーネント（カード） | 印刷向けドキュメント（紙面の設計） |

### 1.2 ユーザーの認知プロセスとのズレ

理事会メンバー（特に法律の専門家でない方）が規約改正案を読むとき、頭の中では以下の順序で理解が進む：

```
① なぜ今、変えなければならないのか？（動機）
② 全部でどのくらいの変更があるのか？（規模感）
③ 何が一番重要なのか？（優先度）
④ 具体的に何がどう変わるのか？（条文の中身）
⑤ うちのマンションに関係あるのか？（文脈化）
⑥ この変更を入れるか入れないか？（判断）
```

**直接生成のWord文書は①〜⑤を丁寧に歩いた上で⑥に至る設計**になっている。
**アプリは④と⑥にフォーカスしており、①②③⑤が弱い可能性がある。**

## 2. 設計原則

以下の5原則をアウトプット品質の指針とする。

### 原則1：課題起点の情報構造（Issue-first, not Article-first）

条文番号順に改正案を並べるのではなく、**「なぜ変えるのか」という課題（issue）を起点**にグルーピングする。

例えば「第2条の定義追加」「第45条の議決権行使」「第46条の出席方法」「第48条の議事録」は、全て**「電子化対応」という1つの課題**に属する。条文を4つバラバラに見せるより、「電子化対応として4条文をまとめて変更する」と見せた方が理解しやすい。

**実装への示唆**: ギャップ分析の結果を「条文リスト」ではなく「課題グループ」にクラスタリングするレイヤーを追加する。

### 原則2：優先度によるナビゲーション（Priority-driven Navigation）

「71条全部を1条目から見てください」は認知負荷が高すぎる。

**「まず法改正で必須の6項目を見ましょう。次に推奨の9項目。最後に将来検討の2項目です」**という優先度ベースのナビゲーションにする。

既存PRDの「重要度（法的必須/推奨/任意）」はデータモデルに存在するが、**UIのナビゲーション導線として優先度順に並べる**ことが重要。

### 原則3：文脈の豊かさ（Rich Context per Item）

各改正項目について、以下の4層の情報を提供する：

| 層 | 内容 | 例 |
|----|------|-----|
| Why | なぜこの変更が必要か（法改正の背景、リスク） | 「2026年4月の改正区分所有法で電磁的方法による議決権行使が法定化されます。現行規約は"書面又は代理人"のみなので、電子投票が無効になるリスクがあります」 |
| What | 何がどう変わるか（現行→改正案の対比） | 現行条文 vs 修正案の新旧対照 |
| How | このマンション固有の影響 | 「189戸のレジデンスでは、海外居住の区分所有者が増加傾向にあり、電子議決権の重要性が特に高い」 |
| So What | 理事会での説明ポイント | 「"法律が変わるので、電子投票もできるように規約を合わせます"と説明すれば十分です」 |

**現行PRDの「4層構造」（①平易な要約、②新旧対照、③理事会向け説明文、④判断ボタン）はこの考え方と整合しているが、①の「要約」が薄い場合、ユーザーはなぜ変えるのか腹落ちしないまま判断を迫られる。**

### 原則4：全体像の先行提示（Overview-first）

個別条文のレビューに入る前に、**必ず全体サマリーを提示**する。

- 全部で何項目の変更があるか
- 優先度別の内訳（必須○件、推奨○件、任意○件）
- カテゴリ別の内訳（法改正対応○件、標準規約対応○件、実務改善○件）
- 想定所要時間

これにより「先が見えない不安」を解消し、計画的なレビューを可能にする。

### 原則5：エクスポートの読み物品質（Print-ready Narrative Quality）

画面上でインタラクティブにレビューするUIと、印刷して配布する文書は**別の設計が必要**。

エクスポートされるWord/PDFは、UIのスクリーンショットではなく、**独立した読み物として成立する品質**でなければならない。

具体的には：
- 表紙・目次がある
- 「本資料の読み方」セクションがある
- 優先度順に構成されている
- 各項目に十分な理由説明がある
- マンション名・日付・免責事項が明記されている
- 印刷時のフォントサイズ・余白が適切

## 3. 具体的な改善要件

### 3.1 ギャップ分析エンジン（F3）の改善

| 要件ID | 要件 | 現状の推定課題 |
|--------|------|--------------|
| Q-01 | 分析結果を「課題（issue）」単位でグルーピングする | 条文単位で個別にギャップが出力され、関連する条文が分散する |
| Q-02 | 各課題に「なぜ変えるのか」の理由文を生成する | ギャップの事実のみで、背景説明が不十分な可能性 |
| Q-03 | マンション固有の文脈（戸数、立地、法人形態等）を理由文に反映する | 汎用的な説明になり、「うちに関係ある」感が薄い |
| Q-04 | 優先度を3段階（必須/推奨/将来検討）で付与し、理由を明示する | 優先度はあるが、判定根拠が不透明な可能性 |

| 要件ID | 要件 | 現状の推定課題 |
|--------|------|--------------|
| Q-05 | 改正案の条文に加え、「理事会での説明一言メモ」を自動生成する | 条文テキストのみで、説明補助がない可能性 |
| Q-06 | 関連する条文を自動的にリンクし、「この変更は第X条と連動します」と表示する | 第45条と第46条が関連することが自明でない |
| Q-07 | テンプレートベース生成の出典を条文レベルで明示する | 「標準管理規約準拠」とだけあり、何条をベースにしたか不明 |

## 4. LLMプロンプトへの示唆

上記の品質を実現するには、LLM（Claude API）へのプロンプト設計が鍵になる。

### 4.1 ギャップ分析プロンプトに追加すべき指示

```
分析結果は以下の形式で構造化してください：

1. 課題グループ（issue_group）としてまとめる
   - グループ名（例：「電子化対応」「所有者不明対策」）
   - グループに含まれる条文番号のリスト
   - グループの優先度（mandatory / recommended / optional）
   - 優先度の根拠（1文）

2. 各課題について：
   - background: この改正がなぜ必要か（法改正の背景を含む）
   - risk: 対応しない場合のリスク
   - condo_specific: このマンション固有の影響（{condoName}、{unitCount}戸、{condoType}を考慮）
   - explanation_hint: 理事会で説明する際のポイント（1〜2文）
```

### 4.2 ドラフト生成プロンプトに追加すべき指示

```
各条文の改正案に加え、以下を生成してください：

- one_liner: この変更を一言で説明するとしたら（理事会での口頭説明用）
- related_articles: この変更と連動する他の条文番号と理由
- source_ref: ベースにした標準管理規約の条文番号
```

### 4.3 エクスポート生成プロンプトに追加すべき指示

エクスポート処理はLLMではなくテンプレートエンジンで行うべきだが、
**各項目の「改正理由」テキストの生成にはLLMを使う**。

```
以下の改正項目について、理事会配布用の説明文を生成してください。

制約：
- 法律の専門用語は使わず、日常語で説明する
- 「なぜ変えるのか」→「何が変わるのか」→「住民への影響」の順で書く
- 1項目あたり100〜150字程度
```

## 5. 実装の優先順位

| 順位 | 要件 | 理由 |
|------|------|------|
| 1 | Q-01: 課題グループ化 | 情報構造の根本改善。他の改善の土台 |
| 2 | Q-02: 理由文の生成 | ユーザーの「なぜ？」に答える。体感品質への影響大 |
| 3 | Q-08〜Q-11: エクスポート品質向上 | 紙配布が最終成果物。ここが弱いと全体の印象が下がる |
| 4 | Q-14: 全体サマリーダッシュボード | レビュー開始前の安心感。実装コスト低 |
| 5 | Q-03: マンション固有文脈の反映 | 「自分ごと」感の向上。プロンプト変更で対応可能 |
| 6 | Q-05: 説明一言メモ | 付加価値の向上。プロンプト追加で対応可能 |
| 7 | 残り | 段階的に対応 |

## 6. まとめ

直接生成のWord文書が「読みやすい」と感じられた理由は、技術的な差ではなく**情報設計の差**である。

核心は3つ：
1. **課題起点 vs 条文起点** → 読者の理解順序に沿った構成
2. **Why の豊かさ** → 「なぜ変えるのか」の説明が各項目に内包されている
3. **全体→詳細の流れ** → サマリーで全体像を掴んでから個別を見る

これらはいずれも、コードの書き換えではなく**LLMプロンプトの改善とUIの情報構造の変更**で実現可能である。
アプリの再現性・スケーラビリティという強みを活かしつつ、上記の設計原則を組み込むことで、
「専門家が手作業で作った文書と遜色ないアウトプット」をアプリから自動生成できるようになる。

## 7. コード分析結果：現状と設計思想とのギャップ

以下は `kiyaku-assist-v2/src/domains/` 配下のコアドメインコード（analyzer.ts, drafter.ts, pdf.tsx, markdown.ts, presentation.ts, retriever.ts）および UI（analysis/page.tsx, review/page.tsx）を精読した結果の分析である。

### 7.1 アプリが既にうまくやっていること（評価点）

コードベースは全体的に質が高く、以下の設計判断は優れている。

| 項目 | 実装内容 | 評価 |
|------|---------|------|
| **構造化出力** | `tool_use` でギャップ分析（5フィールド）とドラフト（8フィールド）をスキーマ強制 | LLMの出力品質を安定させる正しいアプローチ |
| **ドラフトの8フィールド** | draft, summary, explanation, baseRef, impactOnResidents, riskIfUnchanged, transitionalMeasure, standardRuleComparison | 私のWord文書にない `impactOnResidents` `riskIfUnchanged` `transitionalMeasure` は付加価値が高い |
| **文書タイプ別プロンプト** | management-rules / usage-rules / other-bylaws で分岐 | 使用細則に mandatory を使わない等、適切な判断 |
| **マンション属性の反映** | condoName, condoType, unitCount を drafter のプロンプトに組み込み | 原則3（文脈の豊かさ）の一部を実装済み |
| **バッチ処理 + リトライ** | 5件ずつバッチ、2並列、失敗時個別リトライ | 実運用に耐える堅牢な設計 |
| **キャッシュ（30日TTL）** | 同一条文の再分析を回避 | コスト最適化として適切 |
| **レビューUIの判断支援** | 採用/修正/保留 + メモ + 決定支援情報の折りたたみ | PRDの設計に忠実 |
| **PDF の diff 表示** | diffChars() による文字レベルの新旧対照 | 細かい変更を視覚的に把握可能 |

### 7.2 設計思想とのギャップ（改善が可能な箇所）

#### ギャップ A：情報構造が「条文番号順」に固定されている

**現状のコード：**
- `presentation.ts` の `groupExportArticlesByChapter()` は章番号でグルーピング
- `CHAPTER_TITLES` は第1章〜第8章（総則、専有部分等の範囲…）で定義
- エクスポートは常に「第1章→第2章→…→第8章」の条文番号順
- レビューUIも条文リストは基本的に番号順（フィルター可能だが並び替えは限定的）

**設計思想との差分：**
- 原則1（課題起点）が未実装。「電子化対応」「所有者不明対策」といった課題グループの概念がデータモデルにない
- 原則2（優先度ナビゲーション）も部分的。フィルターはあるが、デフォルトの表示順は番号順

**改善案：**
- `GapAnalysisItem` に `issueGroup: string` フィールドを追加
- 分析プロンプトに「関連する条文をグループ名で紐付けよ」と指示を追加
- エクスポート時に「優先度順 + 課題グループ」で並び替えるオプションを追加

#### ギャップ B：分析プロンプトの「Why」が浅い

**現状のプロンプト（analyzer.ts）：**
```
分析の観点:
1. 改正区分所有法（2025年10月施行）への適合性
2. 標準管理規約との乖離度
3. 実務上の重要性
```

出力スキーマの `rationale` は「改正の理由・背景（組合員に説明できるレベル）」と定義されているが、
**5件バッチで処理されるため、1件あたりに割けるLLMの推論リソースが薄くなる。**

**私のWord文書との差分：**
私が書いた「改正理由」は、各項目について法改正の経緯、このマンション固有の事情、対応しない場合のリスクを3段落程度で展開している。5件バッチのrationale は100〜200字程度に留まる傾向が予想される。

**改善案：**
- 分析フェーズでは現状の簡潔なrationaleでOK（コスト効率重視）
- **ドラフト生成フェーズで「読み物としての改正理由」を追加フィールドで生成する**
- drafter の tool_use に `detailedBackground: string` を追加（「この改正の背景を、法改正の経緯とこのマンション固有の事情を含めて300字程度で記述」）

#### ギャップ C：エクスポートに「読み物としてのフレーム」がない

**現状のPDF構造（pdf.tsx）：**
```
ヘッダー（マンション名 + 日付 + 条文数）
  → diff凡例
  → 第1章
    → 条文ごとのカード（メタ表 + 新旧対照 + 要約 + 解説 + 決定支援情報）
  → 第2章
    → ...
フッター（免責事項）
```

**私のWord文書の構造：**
```
表紙（マンション名 + タイトル + サブタイトル + 日付 + 免責）
  → 本資料の概要（なぜ今改正が必要か + 参照法令 + 現行規約の概要）
  → 修正項目一覧（全17項目のサマリーテーブル）
  → 優先度A：最優先で対応すべき項目（6件を詳述）
  → 優先度B：推奨対応項目（9件を詳述）
  → 優先度C：将来検討項目（2件を詳述）
  → 使用細則分析まとめ（10規則の分析サマリー表）
  → 今後の進め方（5ステップ）
  → 免責事項
```

**決定的な差分：**
1. **表紙がない** → 「正式な文書」感が大幅に減る
2. **全体概要セクションがない** → いきなり条文に入るので「なぜ今これを読むのか」が伝わらない
3. **サマリーテーブルがない** → 全体像が掴めない
4. **優先度によるセクション分けがない** → 重要度の軽重が構造レベルで伝わらない
5. **「今後の進め方」セクションがない** → 次のアクションが不明

**改善案（実装コスト低〜中）：**
- PDF/Wordエクスポートに以下を追加：
  1. 表紙（テンプレートで生成、LLM不要）
  2. 全体概要セクション（LLMで1回だけ生成、またはテンプレート + 集計値）
  3. サマリーテーブル（`articles` から集計して自動生成）
  4. 優先度別セクション分け（`importance` でグルーピング、章ではなく優先度を第一ソートキーに）
  5. 「今後の進め方」（テンプレート、condoContext の法人/非法人で分岐）

#### ギャップ D：「このマンション固有の影響」が条文ごとに語られていない

**現状：**
- `buildCondoDescription()` は `マンション名: xxx / 管理組合形態: xxx / 規模: xxx` の3行のみ
- ドラフト生成の system prompt にこの3行が入るが、**条文ごとの影響分析**は `impactOnResidents` フィールドで汎用的に語られるだけ

**私のWord文書との差分：**
例えば項目3（所在等不明区分所有者の除外）で「189戸の大規模マンションである当レジデンスでは、所有者不明・不在化が進行している可能性があり」と書いた。これはマンション固有の事情を踏まえた文脈化。

**改善案：**
- `CondoContext` に追加情報を持たせる：`築年数`, `立地特性（都心/郊外）`, `外国人居住者の有無`, `高齢化状況` 等
- これらをオンボーディング（F0）で取得し、ドラフト生成プロンプトに反映

## 9. 理事会ミーティングから得られた知見（2026-03-28）

### 9.1 ミーティング概要

2026年3月28日に実施された理事会メンバー＋管理会社（日本ハウジング・原田氏）とのミーティングから、アプリの設計前提を大きく変えるべき知見が得られた。

```
  ↓ カスタマイズ
日本ハウジングの各マンション向け標準
  ↓ さらにカスタマイズ
秀和代官山レジデンス向けの完成案
```

原田氏（00:08:18）：「基本は、まず国交省の基準をハウジングなりに各マンションにカスタマイズしてて、ハウジングがさらに秀和に対してカスタマイズして落とし込んでる」

### 9.3 アプリの役割の明確化

**セクション1〜8の設計思想は基本的に正しかった：**
- アプリの核心は「国交省標準 vs 現行規約」の比較分析
- これはどのマンション・管理組合にも普遍的に価値がある

**ミーティングで追加された視点：**
- 管理会社がプロとして改正案を既に作成しているケースがある
- その場合、管理会社案を**オプションの第3レイヤー**として取り込めると価値が増す
- 管理会社が省いた項目が「本当に不要か」の検証ができる

理事メンバー（Speaker 1, 00:07:42）の重要な発言：
「ハウジングが必要としないと言っていても、もしかしたらうちは必要かもしれない」

**→ アプリの核心的価値は「国交省標準 vs 現行規約の意味的比較」であり、管理会社案がある場合は3方向比較に拡張可能。**

### 9.4 比較構造の設計：2層＋オプション1層

**基本構造（全マンション共通）：**

| 比較の軸 | 説明 | 位置づけ |
|---------|------|---------|
| 現行規約 ↔ 国交省標準 | 改正法・標準規約に対する現行規約の乖離分析 | **主軸（必須）** |

**拡張構造（管理会社案がある場合）：**

| 比較の軸 | 説明 | 位置づけ |
|---------|------|---------|
| 現行規約 ↔ 国交省標準 | 上記と同じ | **主軸（必須）** |
| 現行規約 ↔ 管理会社案 | 管理会社の提案内容の確認 | **オプション** |
| 管理会社案 ↔ 国交省標準 | 管理会社が省いた/変えた項目の検証 | **オプション** |

原田氏（00:03:29）：「新しい基準とハウジングの対比はないんです」 — 管理会社自身が持っていない比較軸をアプリが提供できる。

**設計上の重要な判断：** アプリは「管理会社案がなくても完全に機能する」設計にする。管理会社案は常にオプションのインポートであり、アプリの前提条件にはしない。これにより、全国どのマンションでも利用可能になる。

### 9.5 理事会の実際のワークフロー

ミーティングから判明した実際のプロセス：

```
Step 1: 管理会社が改正案を作成（60〜100ページ）← 既に完了
Step 2: 理事会に配布、次回までに各自読み込み
Step 3: 理事会で読み合わせ、「入れたい/外したい」を議論
Step 4: アプリで管理会社案 vs 国交省標準の差分を確認 ← アプリの出番
Step 5: 管理会社案に対する修正要望をまとめる
Step 6: 管理会社が細かい編集・印刷を実施（ここからコスト発生）
Step 7: 催促（臨時総会 or 通常総会で決議）
```

Speaker 1（00:00:00〜00:00:22）：「まず最初に手作業で両方読み合わせ、旧と新をやって右左みたいに分けて。それでどうしても入れ外したくないもんとか、新たに直したいものっていう内容だけ集まって意見出して、その分の読み合わせ的になってきちゃったんですね。」

**重要な含意：**
- アプリは「Step 2の読み込み支援」と「Step 4の差分確認」が主たるユースケース
- 最終的な編集・印刷は管理会社が行うため、アプリのエクスポートは「検討メモ」として機能すればよい（最終成果物ではない）

### 9.6 理事会メンバーが求めるUIの具体像

Speaker 4（00:00:44）：「AIじゃなくても、全部の変更前の情報を条項ごとに、表みたいにしてくれると、じゃあこの証拠はこのままでいい」

**→ 条項ごとの比較テーブル形式が求められている。**
**→ 各条項に対して「このままでいい」という判断UIが自然。**

### 9.7 コスト構造の理解

- 管理会社による比較表作成（60〜100ページ）：**費用なし**（管理契約の一部としてサービス）
- 最終的な細かい編集・印刷：**費用発生**（黒崎が担当）
- **→ アプリは「無料の管理会社サービス」と競合する必要はなく、それを補完する立ち位置が最適**

## 10. 設計思想の更新：ミーティング知見とプロダクトオーナーの方針を反映

### 10.1 原則の修正・追加

セクション2で定義した5原則を、ミーティング知見およびプロダクトオーナー（D）の方針を踏まえて更新する。

#### 原則1（修正）：課題起点 → **意味的分類（Semantic Classification）に再定義**

旧：条文番号順ではなく課題単位でグルーピング
新：**規約の内容を意味的に分類し、最も細かい粒度（条文・項レベル）で比較しつつ、関連するものを意味グループとしてまとめる**

理由：
- 条文番号は管理規約ごとに異なるため、番号順は比較の軸にならない
- 差分（diff）起点だと管理会社案の有無に依存してしまう
- 「電子化対応」「所有者不明対策」「建替え」等のテーマ（意味的分類）は普遍的で、どの規約にも適用可能
- 同じテーマに属する条文が章をまたいで存在することがあり、意味的グルーピングなら自然にまとめられる

**意味的分類の階層構造：**
```
意味グループ（Semantic Group）
  例: 「電子化対応」「所有者不明対策」「マンション再生」
  ↓
  サブテーマ（Sub-theme）
    例: 「電磁的方法による議決権行使」「電磁的方法による総会通知」
    ↓
    最小単位（Clause-level item）
      例: 「第45条第2項」「第46条第1項第3号」
```

この階層構造により：
- 最も細かい粒度で条文を比較できる（理事メンバーの「条項ごとに表で」という要望に対応）
- 関連する複数条文をテーマでまとめて俯瞰できる（「電子化対応として合計N箇所の変更」）
- 条文数が異なる規約同士でも同じ枠組みで比較できる

#### 原則2〜5（維持）

セクション2で定義した原則2（優先度ナビゲーション）、原則3（文脈の豊かさ）、原則4（全体像の先行提示）、原則5（印刷対応の読み物品質）はそのまま維持。

#### 原則6（新規）：管理会社案の柔軟な統合（Optional Third-party Integration）

管理会社案は**オプションの第3レイヤー**として統合できる設計にする。

設計方針：
- アプリは管理会社案がなくても完全に機能する（基本は「現行規約 vs 国交省標準」の2方向比較）
- 管理会社案がある場合はインポートして3方向比較に拡張
- インポートした管理会社案も意味的分類の同じ枠組みで整理される
- 管理会社案にしかない項目、国交省標準にしかない項目をそれぞれ可視化

この設計により、全国どのマンション・管理組合でも利用可能になる。秀和代官山のように管理会社が積極的に改正案を作るケースでも、管理会社がそこまでしないケースでも、同じアプリで対応できる。

#### 原則7（新規）：3カラム比較と改正案生成（Source → Reference → Output）

UIの3カラムは「入力→参考→出力」の流れを左から右に表現する：

| カラム | 内容 | 役割 |
|--------|------|------|
| **左: 現行規約** | 対象マンションの今の条文 | 出発点（Source） |
| **中: 管理会社案**（オプション） | 管理会社の改正提案 | 参考情報（Reference） |
| **右: 改正案** | 国交省標準を踏まえてアプリが生成した改正後の条文 | **成果物（Output）** |

**右カラムの重要性：** 右カラムは単なる「国交省標準の条文」ではなく、国交省標準の内容を踏まえて**このマンションの規約として整形・生成された改正案テキスト**である。条文番号はこのマンションの規約体系に合わせ、文言も現行規約のスタイルを踏襲しつつ改正内容を反映する。

管理会社案がない場合は2カラム（左: 現行規約、右: 改正案）で表示。

#### 原則8（新規）：条項間相互参照の整合性保証（Cross-reference Integrity）

管理規約の条文は他の条文を参照することが多い（例：「第52条に定める〜」「前条の規定にかかわらず」）。改正により条文の追加・削除・番号変更が発生すると、これらの相互参照が不整合になるリスクがある。

アプリは改正案の生成時に、**条項間の相互参照を自動検出・検証し、整合性を保証する**。詳細は10.3節で定義。

### 10.2 意味的分類の設計

#### 10.2.1 なぜ意味的分類が必要か

管理規約の条文番号は各マンションの規約ごとに異なる。例えば「議決権行使」が秀和代官山では第45条だが、別のマンションでは第42条かもしれない。国交省標準とも番号が一致しない。原田氏もミーティングで指摘：「ただ条文がちょっとバラバラになったりするので、その辺がややこしくなる」。

意味的分類であれば、番号に依存せず「議決権行使」という意味で3つのソースをマッピングできる。

#### 10.2.2 分類タクソノミー（案）

以下は2026年改正区分所有法・標準管理規約の改正内容を踏まえた意味的分類の案：

**Tier 1: 意味グループ（8〜12グループ想定）**

| # | グループ名 | 内容の概要 | 改正法との対応 |
|---|----------|----------|-------------|
| 1 | 総則・定義 | 用語定義、適用範囲、管理組合の目的 | 基本的な定義の現代化 |
| 2 | 電子化対応 | 電磁的方法、電子議決権、オンライン総会 | 改正区分所有法の電磁的方法規定 |
| 3 | 所有者不明・不在対策 | 所在等不明者の除外決議、催告の特例 | 改正区分所有法の所在等不明者規定 |
| 4 | 外国籍・海外居住者対応 | 国内代理人、送達先、言語対応 | 改正区分所有法の海外居住者規定 |
| 5 | 総会・議決権 | 普通決議、特別決議、定足数、議事録 | 議決件数要件の変更 |
| 6 | 管理組合運営 | 理事会、役員、管理者、会計 | 管理組合の機関設計 |
| 7 | 専有部分・共用部分 | 使用制限、改修、バルコニー、専用使用権 | 共用部分の変更決議要件 |
| 8 | マンション再生 | 建替え、敷地売却、大規模修繕 | 改正区分所有法の建替え規定 |
| 9 | 生活ルール | ペット、騒音、ゴミ、駐車場、駐輪場 | 使用細則の現代化 |
| 10 | 防災・安全 | 防犯カメラ、防災委員会、緊急時対応 | 防災関連の規約整備 |
| 11 | 名簿・個人情報 | 区分所有者名簿、個人情報保護 | 改正区分所有法の名簿管理規定 |
| 12 | 長期修繕・財務 | 修繕積立金、長期修繕計画、保険 | 修繕計画の法的位置づけ |

**Tier 2: サブテーマ（各グループ内で2〜5個）**

例えば「電子化対応」グループの場合：
- 2-a: 電磁的方法の定義と通知手段
- 2-b: 電子議決権の行使方法
- 2-c: オンライン出席の取扱い
- 2-d: 電磁的方法による議事録の作成・保管

**Tier 3: 最小単位（条文・項レベル）**

例えば「2-b: 電子議決権の行使方法」の場合：
- 第45条第2項「書面又は代理人による〜」→「書面、電磁的方法又は代理人による〜」
- 第45条第3項（新設）「前項の電磁的方法による議決権行使の〜」

#### 10.2.3 意味的分類の生成方法

この分類はLLMで自動生成する。具体的には：

**Step 1: タクソノミー生成（1回のみ）**
- 国交省標準の全条文を読み込み、意味グループとサブテーマの分類体系を生成
- 2026年改正の重点領域を踏まえたグループ設計
- 出力: `SemanticTaxonomy` = グループ名・サブテーマ名・説明のツリー

**Step 2: 現行規約のマッピング（条文単位）**
- 現行規約の各条文・項を、Step 1で生成したタクソノミーにマッピング
- 1つの条文が複数のサブテーマに属する場合もある（例: 第45条は「総会・議決権」と「電子化対応」の両方）
- 出力: `ArticleMapping[]` = { articleRef, semanticGroup, subTheme, relevantText }

**Step 3: 国交省標準のマッピング（同じタクソノミーで）**
- 国交省標準の条文も同じタクソノミーにマッピング
- これにより、番号が違っても意味で対応する条文を紐付けられる

**Step 4（オプション）: 管理会社案のマッピング**
- 管理会社案がインポートされた場合のみ実行
- 同じタクソノミーにマッピングし、3方向比較を可能にする

### 10.3 条項間相互参照の整合性設計

#### 10.3.1 問題の定義

管理規約の条文は他の条文を頻繁に参照する。例：

```
第54条（理事会の議事）
  ２ 理事会の議事については、第52条（※総会の議事録）の規定を準用する。
```

改正により条文の追加・削除が発生すると、番号がずれ、この「第52条」が実際には別の条文を指してしまう可能性がある。現行規約において既に存在するこのような参照関係は、改正後も正しく保たれなければならない。

#### 10.3.2 相互参照のパターン

管理規約に現れる典型的な相互参照パターン：

| パターン | 例 | 検証の必要性 |
|---------|-----|-----------|
| 明示的な条番号参照 | 「第52条に定める〜」 | 番号変更時に必ず更新が必要 |
| 前条・次条参照 | 「前条の規定にかかわらず」 | 条文の挿入・削除で対象がずれる |
| 項番号参照 | 「第45条第2項の〜」 | 項の追加・削除で対象がずれる |
| 章・節参照 | 「第7章に定める〜」 | 章構成の変更で対象がずれる |
| 準用規定 | 「〜の規定を準用する」 | 準用先が改正された場合の整合性 |
| 使用細則への委任 | 「細則に定めるところにより」 | 細則側の対応条文との整合 |

#### 10.3.3 相互参照グラフの構築

改正案を生成する際に、以下のデータ構造を構築する：

```typescript
interface CrossReference {
  sourceArticle: string;       // 参照元: "第54条第2項"
  targetArticle: string;       // 参照先: "第52条"
  referenceType:
    | "explicit"               // 明示的番号参照
    | "relative"               // 前条・次条
    | "chapter"                // 章・節参照
    | "delegation"             // 細則委任
    | "application";           // 準用
  originalText: string;        // 参照を含む原文: "第52条の規定を準用する"
  context: string;             // 参照の意味的文脈
}

interface CrossReferenceGraph {
  references: CrossReference[];

  // 特定の条文を参照しているすべての箇所
  getReferencesTo(article: string): CrossReference[];

  // 特定の条文が参照しているすべての条文
  getReferencesFrom(article: string): CrossReference[];

  // 条文番号の変更による影響範囲
  getImpactOfRenumber(oldArticle: string, newArticle: string): CrossReference[];
}
```

#### 10.3.4 整合性検証のフロー

```
Step 1: 現行規約の相互参照グラフを構築
  入力: 現行規約のテキスト
  処理: LLMで条文間の参照関係を抽出
  出力: CrossReferenceGraph（現行）

Step 2: 改正案の生成
  入力: 現行規約 + 国交省標準 + 意味的分類 + (管理会社案)
  処理: 条文ごとの改正案テキスト生成
  出力: 改正案テキスト（暫定版）

Step 3: 改正による番号変更マップの生成
  入力: 現行の条文構成 vs 改正案の条文構成
  処理: 条文の追加・削除・移動を検出し、番号変更マップを作成
  出力: RenumberMap = { "旧第52条" → "新第53条", ... }

Step 4: 相互参照の自動更新
  入力: 改正案テキスト（暫定版）+ RenumberMap + CrossReferenceGraph
  処理: 改正案テキスト内のすべての参照番号を新番号に更新
  出力: 改正案テキスト（参照更新版）

Step 5: 整合性検証
  入力: 改正案テキスト（参照更新版）
  処理:
    a) 参照先が実在するか確認（存在しない条文への参照がないか）
    b) 準用先の改正内容との整合確認（準用元の意図と一致するか）
    c) 前条・次条の相対参照が正しい条文を指しているか確認
  出力: IntegrityReport = { valid: CrossReference[], warnings: CrossReference[], errors: CrossReference[] }
```


## 11. 更新後の全体まとめ

### 11.1 アプリのポジショニング

```
「国交省標準と現行規約を意味的に分類・比較し、
 改正案テキストの生成から相互参照の整合性検証まで、
 理事会の改正検討を端から端まで支援するツール」

- 管理会社案がない場合 → 2カラム（現行 vs 改正案）で完全に機能
- 管理会社案がある場合 → 3カラム（現行/管理会社案/改正案）に拡張
- どのマンション・管理組合でも使える汎用性
- 最終成果物は「相互参照検証済みの改正案文書」
```

### 11.2 設計原則（最終版・8原則）

1. **意味的分類による情報構造**（Semantic Classification）— 条文番号ではなくテーマ・意味でグルーピング。最小粒度（条文・項）まで分類し、関連するものをまとめる
2. **優先度ナビゲーション**（Priority-driven）— 法的必須→推奨→任意の順
3. **文脈の豊かさ**（Rich Context）— Why/What/How/So Whatの4層
4. **全体像の先行提示**（Overview-first）— サマリーダッシュボード→詳細
5. **印刷対応の読み物品質**（Print-ready）— 読み合わせ会で使える紙面設計
6. **管理会社案の柔軟な統合**（Optional Third-party Integration）— なくても機能する。あれば中カラムに表示
7. **Source→Reference→Outputの3カラム**（Left-to-Right Flow）— 左=現行、中=管理会社案（任意）、右=生成された改正案
8. **条項間相互参照の整合性保証**（Cross-reference Integrity）— 改正による番号変更に伴う参照の自動更新・検証

### 11.5 残存する設計判断事項

1. **タクソノミーの粒度設計**: 意味グループの数（8〜12個の想定）とサブテーマの粒度を、実際のユーザーテストで検証する必要がある
2. **条文の多重所属**: 1つの条文が複数の意味グループに属する場合の表示方法（リンク表示 vs 重複表示）
3. **マッピング精度の保証**: LLMによる意味マッピングの精度をどう担保するか（人間レビューフェーズを挟むか）
4. **管理会社案のインポート形式**: Word (.docx) vs PDF — 管理会社の納品形式に依存
5. **条文番号のズレ問題**: 原田氏指摘「条文がバラバラになる」→ 意味的分類により番号ではなく意味でマッピングするため、本質的に解決される設計
6. **タクソノミーの更新**: 法改正が進むとテーマが変わる。タクソノミーを固定にするか、毎回生成するかの判断
7. **改正案テキストの生成品質**: 右カラムの改正案テキストはLLMが生成するが、法律文書としての正確性をどう担保するか。人間レビュー必須のフラグ付けが必要
8. **相互参照検証の限界**: 「前条」「次条」等の相対参照や、使用細則への委任規定は、機械的な番号置換では対応できないケースがある。LLMによる意味的検証との併用が必要
9. **再採番のタイミング**: 条文の追加・削除が確定するまで再採番できないため、検討フェーズでは暫定番号を使い、確定フェーズで一括再採番する設計が妥当
